# RU: AdGuard Home и купленный HTTPS-выход без VPN у клиента

По состоянию на 24 ноября 2026 года сценарий развёрнут вручную и работает на RU VPS. Для клиента достаточно именного DoT или DoH. Управление этой схемой из Telegram-бота и установка с чистого сервера штатным установщиком Комбайна ещё требуют отдельной реализации и проверки.

## Как устроен маршрут

1. Клиент отправляет DNS-запрос в AdGuard Home. Для обычных доменов работают штатные DNS-ответы и фильтры. Для выбранных доменов DNS-подмена возвращает адрес RU VPS.
2. Клиент открывает HTTPS к этому адресу. Входящий IPv4 TCP/443 перенаправляется в потоковый nginx на TCP/9440. nginx выбирает обработчик по SNI. Для выбранных ИИ-доменов он передаёт HTTPS локальному Xray на TCP/9443. Xray берёт выход SOCKS5 или HTTP из существующего `aiproxy` и отправляет трафик через купленный прокси.
3. Для имени самого DoH nginx направляет соединение в свой локальный TLS-обработчик на TCP/9445 и передаёт DNS-запрос в AdGuard на `127.0.0.1:3000`. DoT принимает сам AdGuard на TCP/853. Остальные подключения на общем входе TCP/443 возвращаются существующему Xray/VLESS. Веб-панель AdGuard доступна отдельно на TCP/8443 с ограничением по IP администратора.

DNS-подмены указывают на RU VPS. Если подставить адрес купленного прокси прямо в DNS, обычный HTTPS-клиент не выполнит SOCKS5 или HTTP CONNECT. Для этого в схеме есть локальный Xray.

## Последовательность работ и решения

1. На RU проверили оба варианта подключения к купленному прокси, SOCKS5 и HTTP. Сохранили рабочий вход VLESS. Вариант с отдельным каскадом VLESS между RU и зарубежным VPS оставили отдельной задачей.
2. Развернули AdGuard Home из официального релиза и сверили SHA-256 архива. Запустили AdGuard и отдельный Xray-релей, взяли купленный выход из действующей конфигурации Комбайна. Начали с одного тестового домена, затем расширили списки DNS-подмен и SNI. При изменении списка доменов для этого режима должны совпасть назначения в AdGuard, nginx и Xray. Список `data/ai-proxy-domains.txt` относится к режиму `aiup` для VLESS.
3. Подключили DNS-имя и сертификаты. Для DoT отдельный ClientID задаётся именем `<id>.<dns-host>`, для DoH — путём `/dns-query/<id>`. Для именных DoT-поддоменов использованы wildcard DNS и wildcard-сертификат. Продление сертификата с ручным DNS-01 нужно отслеживать отдельно.
4. Перевели устройства на именные адреса. В AdGuard заполнили `allowed_clients` идентификаторами клиентов и локальными адресами `127.0.0.1` и `::1`. Админка на TCP/3000 слушает loopback. TCP/UDP 5300 закрыт снаружи, внешний порт 53 не открыт.
5. Включили `nftables` в автозагрузку. Для входящего и транзитного трафика политика `drop`, для исходящего — `accept`. Разрешены loopback, established/related, ICMP/ICMPv6, DHCP и нужные входы TCP 22, 80, 443, 853, 8443. TCP/9440 принимает трафик, перенаправленный с TCP/443. `/etc/nftables.conf` очищает только `inet filter` и сохраняет отдельные таблицы перенаправления и защиты DNS.
6. При внешней проверке обнаружили, что общий DoH `/dns-query` обслуживался без ClientID. Потоковый вход nginx пересоздаёт соединение на loopback, поэтому следующий nginx передаёт AdGuard локальный IP, который есть в списке разрешённых. В правиле nginx сделали сегмент `/<id>` обязательным и ограничили его известными ClientID. Остальные пути возвращают HTTP 404. Перед правкой сверили именные DoT и DoH на Keenetic, сделали копию файла, выполнили `nginx -t` и применили конфиг через reload.
7. Обнаружили, что пакетное `ExecStop` на RU выполняет `nft flush ruleset`. Даже после устранения глобальной очистки в конфиге обычный `systemctl restart nftables` удалял бы таблицы AdGuard. Добавили `/etc/systemd/system/nftables.service.d/90-preserve-rules.conf` с `[Service]` и пустым `ExecStop=`. После `daemon-reload` проверили, что настройка загружена, проверили конфиг через `nft --check --file /etc/nftables.conf` и выполнили контрольный restart. Теперь при остановке сервиса правила остаются в ядре. Основной конфиг при следующем запуске пересобирает только свою таблицу.

## Что проверено на RU

- После reload nginx и контрольного restart nftables общий DoH возвращает HTTP 404, именной DoH — HTTP 200 и DNS RCODE 0.
- Именной DoT вернул DNS-ответ. DoT без ClientID установил TLS, но DNS-запрос получил REFUSED.
- После restart на месте `ip adguard_ai_https`, `inet adguard_ai_dns_guard` и `inet filter`.
- Телефон на мобильной сети виден в журнале под своим ClientID с протоколом DNS-over-TLS. В журнале видны и блокировки, и DNS-подмены. На RU подтвердили работу ChatGPT и Gemini, в том числе Gemini на Android без Hiddify.
- «Топ клиентов» хранит и строки, агрегированные по IP. Текущие запросы конкретного устройства проверяются по времени, ClientID и протоколу в журнале.
- Отдельно остаются приёмочные проверки чистой установки, повторной установки, перезагрузки всего VPS и интеграции с Telegram. Проверку сохранения правил при restart службы выполнили отдельно.

## Эксплуатация и перенос в Комбайн

- При добавлении клиента согласованно обновлять запись клиента, `allowed_clients` и правило nginx для именного DoH. Для DoT проверить DNS-поддомен и покрытие сертификатом. Бэкапы на стенде сделаны перед каждой изменяемой группой настроек: конфиг nftables, конфиг AdGuard и vhost DoH.
- PR [#1](https://github.com/ln71v/kombain/pull/1) описывает сценарий A, в котором бот принимает строку прокси для клиентов VLESS через `aiup`. Для RU-сценария без VPN нужно отдельно связать DNS-режим с этим купленным выходом. Текущая команда `aiproxy install` отвечает за другой вариант установки и не должна запускаться поверх ручного RU-стенда.
- Контракт будущего режима: принять прокси через существующий защищённый ввод, проверить его с VPS, сохранить действующий VLESS, развернуть именные DoT/DoH и локальный HTTPS-релей, оставить внешний DNS 53 закрытым. При сбое восстановить прежние конфиги и правила. Повторная установка и обновление должны сохранять клиентские идентификаторы и настройки сертификатов.
- До релиза проверить на отдельном VPS установку и повторный запуск, отказ неизвестному клиенту, обычный сайт, выбранный ИИ-сервис с реального телефона без VPN, существующий VLESS, restart nftables, reboot VPS и откат. Для ремонта рабочего RU применять только действия, которые относятся к нужной службе.
